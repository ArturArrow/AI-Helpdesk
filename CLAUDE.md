## Project status

Early-stage, through the auth phase and starting on user management. PostgreSQL + Prisma are wired up (`server/prisma/schema.prisma`, twelve migrations, an idempotent admin `seed.ts`), and Better Auth provides session auth with a `role` field on users (`server/src/lib/auth.ts`, `requireAuth` / `requireAdmin` middleware). The client has routing, a protected layout, a login form built on shadcn, and an admin-gated `/users` page that lists users from `GET /api/users` and creates, edits and soft-deletes them in dialogs (`server/src/routes/users.ts`). Vitest + React Testing Library component tests cover the pages, forms, navbar and client routing (`bun run --filter client test`), and `bun:test` unit tests cover the AI prompts (polish, summary, classification, auto-resolve) (`bun run --filter server test`). Playwright runs against a separate `helpdesk_test` database, with 426 passing E2E tests covering auth (login, sessions, logout, route gating, the API guards), creating, editing and soft-deleting users, the inbound-email webhook (including reply threading and attachments), attachment downloads, `GET /api/tickets`, `GET /api/tickets/:id`, the ticket replies API and the dashboard's `GET /api/tickets/stats` (`e2e/TEST_SUMMARY.md`). New tests default to component tests; see *Choosing a test layer*.

A `Ticket` model exists, and inbound email creates tickets through a secret-guarded webhook (see *Inbound email* below). Any signed-in user can list tickets on `/tickets` (`TicketsPage` / `TicketsTable`) from `GET /api/tickets` (`server/src/routes/tickets.ts`, mounted behind `requireAuth` only). **Sorting and filtering happen on the server:** `?sortBy=subject|senderName|status|category|createdAt&sortOrder=asc|desc` (`ticketListQuerySchema` in `core/schemas/tickets`, default `createdAt desc`), with tie-breaks on `createdAt desc, id desc` and unclassified tickets last; `?status=open|resolved|closed` (absent = those three: `new` and `processing` tickets, which the AI is still handling, are never listed, and those two values are rejected) and `?category=<TicketCategory>|unclassified` filter (absent = all, `unclassified` = null category), and `?q=` is a case-insensitive substring search over subject, sender name, sender email and body (trimmed, max 200). **Prisma passes `contains` to `LIKE` unescaped** (`%` matched every row), so the route escapes `%`, `_` and `\` with `escapeLike` first; do the same for any other `contains`/`startsWith`/`endsWith` on user input. **Paginated:** `?page=` (1-based, default 1, max 1,000,000 so Prisma's 32-bit `skip` can't overflow) and `?pageSize=` (default 10, max 100, `DEFAULT_TICKET_PAGE_SIZE` / `MAX_TICKET_PAGE_SIZE`); the response is `{ tickets, total }`, with the page and the count read in one `$transaction`. A page past the end returns `[]` with the real total. The page keeps the filters, the sort and the page number in its own URL (`/tickets?status=open&q=refund&sortBy=subject&sortOrder=asc&page=2`, defaults left out, read with `useSearchParams` and validated with the same schema, invalid values ignored) so a list can be linked to, e.g. from the dashboard's quick filters. Each group (filters, sort, page) is parsed separately, so an invalid value falls back to that group's default without dropping the rest. **The sort must stay in the URL with the page:** as component state, re-sorting on page 2 rendered once with the new sort and the old page (react-router applies the URL change in a separate render) and sent a stray request. `TicketsTable` is therefore controlled (`sort`/`onSortChange`, `page`/`onPageChange`), and the pagination footer reads the page of the data on screen, not the URL, so it doesn't run ahead while the next page loads. The search box keeps its own text and writes `q` 300 ms after typing pauses, replacing the history entry rather than pushing one. Any filter, search or sort change resets to page 1. `TicketFilters` uses the shadcn/Base UI `Select` with a `null` item for "all"; pass the value type explicitly (`<Select<VisibleTicketStatus>>`), since inference from `items` picks the wrong type. Status and category labels (`statusLabels`, `categoryLabels`) live next to their enums in `core/constants/ticketStatus` and `core/constants/ticketCategory`. Status and category are Postgres enums, so they sort in declaration order, not by label. The table is TanStack Table **v9** (`@tanstack/react-table`, `useTable` + `tableFeatures({ rowSortingFeature })`, `manualSorting: true`): it only tracks the sorted column and renders rows in the order the API returns them. Column ids are the `sortBy` values. Most TanStack examples online are v8 (`useReactTable`, `getCoreRowModel`) and won't match.

**Detail:** the subject in the table links to `/tickets/:id` (`TicketDetailPage`), with editable assignee, status and category (below), from `GET /api/tickets/:id`. The id is validated with `ticketIdParamsSchema` via `validateParams` (`server/src/lib/validate.ts`); bad id → 400, missing → 404. The response has the plain-text `body`, the sender's raw `bodyHTML: string | null` and `assignedTo: { id, name } | null` (looked up separately, since `assignedToId` has no relation). `TicketDetail` renders `bodyHTML` when present and falls back to `body`. **The HTML is unsanitized and comes from the sender**, so it is only ever rendered through `emailContent` (`client/src/lib/emailHtml.ts`), which runs `DOMPurify.sanitize`; never pass it to `dangerouslySetInnerHTML` without that. **Updating:** the detail page's "Assigned to", "Status" and "Category" fields are `Select`s that save on change through one page-level mutation, `PATCH /api/tickets/:id` with only the changed field (`updateTicketSchema`: optional `assignedToId: string | null`, `status` (only `VISIBLE_TICKET_STATUSES`; a `new`/`processing` ticket shows its label but agents can't pick those), `category: TicketCategory | null`, at least one required; `null` unassigns or marks unclassified). Any signed-in user may update. All three selects are disabled while a save is pending, and a failure shows one "Couldn't update the ticket" alert. The assignee options come from `GET /api/tickets/assignees` (active users with `Role.agent`, `{ agents: [{ id, name }] }`, declared before `/:id` so it isn't read as an id), with a `null` "Unassigned" item. The server answers 404 for a missing ticket and 400 unless a non-null `assignedToId` is an active agent, and returns the same shape as the detail GET, which the page writes straight into its query cache. Deleting an agent unassigns their tickets (see user management below); a ticket that still holds a soft-deleted agent (assigned before that rule) shows them as the current value, but they can't be picked again. The link passes the list's URL in router `state.from`, so "Back to tickets" returns to the same filters, sort and page.

**Replies:** under the ticket body, `ReplyThread` lists the ticket's replies and `ReplyForm` sends a new one; both are keyed on `repliesQueryKey(ticketId)` (`client/src/lib/replies.ts`), and the form appends the created reply to that cache instead of refetching. The `Reply` model has `bodyHTML` (nullable, like the ticket's: the raw HTML of a customer's email, always null for agent replies, which are plain text; returned by both endpoints and rendered by `ReplyThread` only through `emailContent`, falling back to `body`), `sender: ReplySender` (`agent` | `customer` | `ai`, mirrored in `core/constants/replySender` with `replySenderLabels`), `authorId` (the agent; null for `customer` and `ai`), `messageId` (unique, the customer email's Message-ID; null for agent replies) and `ticketId` with `onDelete: Cascade`. Tell the two apart by `sender`, never by whether `authorId` is null. `server/src/routes/replies.ts` (`Router({ mergeParams: true })`, mounted inside `ticketsRouter` as `/:id/replies`, so it inherits `requireAuth`) serves `GET /api/tickets/:id/replies` (`{ replies }`, oldest first) and `POST` (`createReplySchema` in `core/schemas/replies`, `201 { reply }`), both 404 for a missing ticket. POST always writes `ReplySender.agent` with the signed-in user as author. **Emailing replies:** with `MAILER_URL` and `MAILER_SECRET` set, every agent reply (POST above) and AI reply (auto-resolve) is stored with `emailStatus: pending` (`EmailStatus` enum, mirrored in `core/constants/emailStatus` with `emailStatusLabels`) and queued on `send-reply-email` (`queueReplyEmail` in `server/src/lib/queue.ts`; a failed queue send marks it `failed`). The worker, `sendReplyEmail` (`server/src/lib/sendReplyEmail.ts`), posts it to the mailer's `/send` as `Re: <subject>` to `ticket.senderEmail`, with `In-Reply-To`/`References` built by `threadHeaders` from the ticket's and earlier replies' Message-IDs (first + latest 99 past 100), then stores the returned Message-ID on `Reply.messageId` with `sentAt` and `sent`, so the customer's answer threads through the webhook's existing lookup. Only a `pending` reply is sent, so a retry after success doesn't resend; the remaining gap is a send that succeeded with the DB write failing. A 400 from the mailer marks it `failed` at once; other errors are retried like the AI jobs, and the last attempt marks it `failed`. Without the mailer `emailStatus` stays null (dev without a mail server, E2E) and nothing is queued. `ReplyThread` shows the status label after the time ("Not sent" in `text-destructive`) and refetches every 5 s while any reply is pending. `autoResolveNewTicket` returns the AI reply's id and the queue worker queues its email, which keeps `autoResolveTicket.ts` from importing `queue.ts` (a cycle). **Polish:** the form's "Polish" button sends the draft to `POST /api/tickets/:id/replies/polish` (same `createReplySchema` body, `{ body }` back, nothing stored, 404 for a missing ticket, 503 without `OPENAI_API_KEY`), which, with the ticket's subject, sender and body and its latest 20 replies as context (plain-text bodies only, each capped at 4 000 characters, `<` escaped and framed in the prompt as data rather than instructions), loaded by `loadTicketContext` (`server/src/lib/ticketContext.ts`), rewrites it with OpenAI `gpt-6-luna` (`reasoningEffort: "low"`) through the Vercel AI SDK (`ai` + `@ai-sdk/openai`, `polishReply` in `server/src/lib/ai.ts`) greeting the customer by the first word of `senderName` and signing with the signed-in agent's name and `SIGNATURE_URL` (both in the prompt's `<reply-details>`; the model words the greeting and closing in the draft's language), and replaces the textarea's text; both buttons are disabled while either request is pending. `customer` replies come from the inbound-email webhook (see *Inbound email*).

**Summary:** `TicketSummary`, right under the ticket body, has a "Summarize" button that calls `POST /api/tickets/:id/summary` (no body, `{ summary }` back, 404 for a missing ticket, 503 without `OPENAI_API_KEY`). It's a `useMutation`, not a query, so every click regenerates the summary from the thread as it is now; nothing is stored or cached. The route uses the same `loadTicketContext` and prompt framing (`threadPrompt`) as Polish, with `summarizeTicket` in `server/src/lib/ai.ts` (English, plain text).

**Dashboard:** `/` is `DashboardPage`, five cards from `GET /api/tickets/stats` (in `ticketsRouter` before `/:id`, any signed-in user, `TicketStats` in `core/constants/ticket`): `{ total, open, resolvedByAi, averageResolutionMs }`. `total` counts every ticket, `new`/`processing` included; `resolvedByAi` counts resolved/closed tickets that have a `ReplySender.ai` reply; `averageResolutionMs` (null when nothing is resolved) averages `resolvedAt - createdAt` over resolved/closed tickets with a raw query, since Prisma's `aggregate` can't average a difference. `?period=7d|30d|90d|all` (`ticketStatsQuerySchema`, default `all`) limits `total`, `resolvedByAi`, the average and `ticketsPerDay` to tickets *created* in the period, so the AI share compares the same tickets; `open` is always the live backlog (its card says "(now)"). Periods are calendar days, today included, in `?tz=` (an IANA zone, default `UTC`; the page sends the browser's), so `ticketsPerDay` (`{ date: 'YYYY-MM-DD', count }[]`, every day from the period start, or the first ticket for `all`, to today, zeros included) sums to `total`. `TicketsPerDayChart` draws it under the cards as plain CSS bars with a hover label and a visually hidden table; no chart library. **Date maths stays in SQL:** `createdAt` is a UTC `timestamp` without a zone and the dev database's session zone is local (Europe/Warsaw), and a `timestamptz` read back through the Prisma adapter lost its offset, so the route converts explicitly (`AT TIME ZONE 'UTC' AT TIME ZONE tz`) and passes dates to JS only as UTC text. The page keeps the period in its URL (`/?period=30d`, `all` left out, invalid values ignored) and computes the AI share as `resolvedByAi / total`. The total and open cards link to `/tickets` and `/tickets?status=open`. **`Ticket.resolvedAt`** is set when a ticket becomes resolved or closed and cleared when it's reopened, in three places: `PATCH /api/tickets/:id` (`resolvedAtFor`, which keeps the time when a ticket moves between resolved and closed), the AI auto-resolve, and the webhook's reopen on a customer reply. Any new code that changes a ticket's status must keep it in step. Rows that were already finished before the column existed were backfilled with `updatedAt`.

Not yet built: creating tickets by hand, resending a reply whose email failed, the remaining AI features (suggested replies), and the rest of the dashboard (category breakdown, recent tickets). See `project-scope.md`, `tech-stack.md`, and `implementation-plan.md` for the intended design and build order before adding features, since the target architecture below is still ahead of the current state.

## UI components (shadcn)

The client uses **shadcn** on top of Tailwind v4, initialized with `--preset nova` → style `base-nova`. Components are built on **Base UI** (`@base-ui/react`); there is no `@radix-ui/*` dependency. Most shadcn examples online are Radix-era and will not match — resolve the Base UI variant via context7 before pasting a snippet.

- Add components with `bunx shadcn@latest add <name>` (config in `client/components.json`).
- Imports use the `@/` alias → `client/src`. It is declared in `client/vite.config.ts` (via `import.meta.dirname`, since the package is ESM and `__dirname` is undefined there) and in `paths` in both tsconfigs. **Do not add `baseUrl`** — this repo is on TypeScript 6, where it is deprecated and fails the build with TS5101; `paths` alone resolves relative to the tsconfig. shadcn's own docs still tell you to add it.
- `cn` is re-exported from the `cn` package in `src/lib/utils.ts`, not hand-written over clsx + tailwind-merge.
- Use theme tokens (`bg-muted`, `text-destructive`, `bg-card`) rather than hardcoded palette colors (`bg-gray-50`, `bg-blue-600`), so pages follow the theme's dark mode. `ProtectedLayout.tsx` and `Navbar.tsx` still use hardcoded grays and are due for conversion.

**Keep `client/src/components/ui/` to components with a live importer.** Deleting unused ones is not just tidiness: Tailwind v4 scans source files, so an unimported component still emits its CSS. Removing `field.tsx` + `separator.tsx` cut the CSS bundle from 38.46 kB to 31.16 kB. Re-adding is one CLI call.

### Form conventions

Forms use react-hook-form + zod (`zodResolver`) with **`register()`**, not `Controller`. Base UI's `Input` renders a real `<input>`, forwards the ref, and supports uncontrolled mode, so `register` works — shadcn's docs recommend `Controller` for consistency with genuinely controlled components (Select, Checkbox), but it is not required for text inputs.

Markup is plain: a `div` wrapper with spacing classes, `Label` + `htmlFor`, `Input` with `aria-invalid`, and `<p role="alert" className="text-sm text-destructive">` for the message. The `Field`/`FieldGroup`/`FieldError` family is deliberately not used — it is presentational only (`Field` is a `div` with `role="group"` and a few utility classes) and was removed. Prefer the plainest construct that works; add a wrapper only when it carries real behavior. See `client/src/pages/LoginPage.tsx` for the reference shape.

### Choosing a test layer: component tests first

**Rely mostly on component tests; write an E2E test only when necessary.** Component tests are fast, need no database or consent, and run on every change; each E2E run resets `helpdesk_test` and needs the user's go-ahead.

- **Component test** (the default) for anything the client decides: what a page or form renders, loading/empty/error states, validation messages, labels and formatting, the order rows are shown in, navbar links, and client routing and redirects (`App.test.tsx` renders the routes with a mocked session). Mock the HTTP call.
- **E2E test** only for what needs the real server and database: server auth and role guards (401/403), what an endpoint actually stores or returns (fields, sorting, dedupe, validation responses), Better Auth behaviour (sign-in, sessions, soft-deleted users), and a flow whose correctness depends on client and server together. Test these at the API level (`request`) where possible; drive the browser only when the point is the full stack in the UI.
- **Server unit test** (`bun:test`, `server/src/**/*.test.ts`, next to the code) for server logic that neither of the above can reach, like what's sent to an external API. `server/src/lib/ai.test.ts` is the reference: it replaces `@ai-sdk/openai` and `./env` with `mock.module` and *then* loads `./ai` with `await import(...)` (a static import would load the real modules first), and the fake provider returns a `MockLanguageModelV4` from `ai/test` whose `doGenerateCalls` hold the prompt that was sent. No test reaches OpenAI, and none needs `.env` or a database, so run them freely. Don't put tests that need the database here; those are E2E.
- Don't duplicate: if a component test already covers a UI behaviour, don't re-check it in E2E. The `/tickets` page is the reference split — UI in `TicketsPage.test.tsx`, `Navbar.test.tsx` and `App.test.tsx`; only the `GET /api/tickets` API tests in `e2e/tests/tickets.spec.ts`.

### Writing component tests: use the `component-test-writer` agent

**Always delegate writing, extending or fixing component tests** (Vitest + React Testing Library, `client/src/**/*.test.tsx`) to the project subagent `component-test-writer` (`.claude/agents/component-test-writer.md`, via the Agent tool with `subagent_type: "component-test-writer"`). Don't write test files in the main session. The agent file holds the harness and the conventions, and nothing about them is repeated here.

- **In the prompt,** say what to cover (the component and the states or cases the user asked for) and what changed, if the tests are for new work from this session.
- **It runs the checks itself:** `vitest run`, `tsc -b` and lint. It also breaks the covered code once to prove the tests can fail, then restores it. No database is involved, so no consent is needed, and you can run `bun run --filter client test` any time.
- **It edits only** `client/src/**/*.test.tsx` and `client/src/test/`. If it reports that the app needs a change (e.g. a missing accessible name) or a new package (e.g. `@testing-library/user-event`), make it in the main session with the user's go-ahead, then send the agent back.
- **Afterwards,** relay its report, since the user doesn't see it: the files and tests added, the results and the break-it check. Then run `git diff --stat` to confirm the app files are unchanged.

### Writing E2E tests: use the `e2e-test-writer` agent

**Always delegate writing, extending or fixing Playwright tests to the project subagent `e2e-test-writer`** (`.claude/agents/e2e-test-writer.md`, via the Agent tool with `subagent_type: "e2e-test-writer"`). Don't write specs in `e2e/` directly in the main session. The agent file holds the harness details (ports, `helpdesk_test`, global setup and teardown, the root tsconfig) and the test conventions, and nothing about them is repeated here.

In the prompt, give it what it can't work out on its own:
- **What to cover:** the page or flow (e.g. "login: happy path, validation errors, wrong password") and anything the user specifically asked for.
- **What changed:** if the tests are for new work from this session, which files or routes changed.
- **Don't pass consent to run.** In practice the agent refuses consent relayed through another agent, even quoted verbatim, so it only type-checks and lists the tests. Plan on running the suite yourself afterwards (below).

**Afterwards:** the agent's report isn't shown to the user, so relay it. That means which specs were added and what each covers, the results of `tsc`, `--list` and the run (or that it didn't run), and any app change it said is needed to make something testable. The agent also rewrites `e2e/TEST_SUMMARY.md` every time it changes tests. The agent edits only `e2e/**` and, when needed, `playwright.config.ts`. It never touches `client/`, `server/` or `.env*`. If it reports that the app needs a change (e.g. a missing accessible label or endpoint), make that change in the main session with the user's go-ahead, then send the agent back to finish.

**Running the suite yourself.** Each run resets `helpdesk_test`, and Prisma refuses that reset from Claude Code without the user's explicit consent. So ask first, then run `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION="<their exact message>" bun run test:e2e --reporter=line`. Consent covers one run: ask again after further changes. Then update the "Last run" line in `e2e/TEST_SUMMARY.md` with the result.
- `webServer` never reuses a running server. If ports 3101/5174 are taken, the run fails with "…/api/health is already used". Usually that's the user's own `test:e2e:ui` window, so ask them to close it rather than killing the process.
- Moving files or fixing import paths under `e2e/` is fine to do directly. Writing or changing test logic still goes to the agent.

## Authentication

Better Auth (`better-auth`) with the Prisma adapter, email + password only, DB-backed sessions. Configured in `server/src/lib/auth.ts`.

**Sign-up is disabled** (`disableSignUp: true`). There is no public registration path and none should be added: the admin comes from `bun run db:seed`, and agent accounts are meant to be created by an admin (see *Creating accounts* below). A login form that offers "create an account" would have nothing to call.

**Roles.** `Role` is a Prisma enum (`admin` | `agent`, default `agent`) and a Better Auth `additionalFields` entry declared `input: false` — it is server-owned and never accepted from API input. Do not try to set `role` through a client-side sign-up/update payload; change it in the database or the seed. **Never write a role as a string literal** (`'admin'`, `"agent"`) in app code — not in comparisons, types, defaults or payloads. Use the enum for the side you're on:

- **Server:** the generated Prisma enum, `import { Role } from "../../generated/prisma/enums"` → `Role.admin`, `Role.agent`. `enums.ts` holds only the const object, so the import doesn't pull in the Prisma client. `server/src/routes/users.ts` and `middleware/requireAdmin.ts` are the reference.
- **Client (and anything else outside the server):** `import { Role } from 'core/constants/role'` — a TS string `enum` with the same `Role.admin` / `Role.agent`, also used as the type for fields (`role: Role`, as in `UsersTable`'s `User`). `core/src/constants/` holds one file per enum (`role.ts`, `ticketStatus.ts`, `ticketCategory.ts`, `replySender.ts`). They are real `enum`s, which is why `erasableSyntaxOnly` is off in `client/tsconfig.app.json` (it rejects enums even in `core` files the client imports; Vite and Bun both compile them). The client may not value-import the server's generated enum (only `import type` crosses that boundary, see *Client wiring*), which is why it's restated in `core`.
- **Keeping them in sync:** `core/src/constants/*.ts` mirror the Prisma enums (`Role`, `TicketStatus`, `TicketCategory`, `ReplySender`) by hand. `server/src/lib/enumsInSync.ts` fails the server's `tsc` (`bun run --filter server typecheck`) if any pair differs — the client build doesn't see that file, so run the server typecheck after touching an enum. Adding a role means editing `schema.prisma` (plus a migration), `core/src/constants/role.ts`, and the `type` list of the `role` field in `auth.ts`; adding a ticket status, the first two. **Adding a ticket category:** (1) the value and its `categoryLabels` entry in `core/src/constants/ticketCategory.ts`; (2) the same value in `enum TicketCategory` in `schema.prisma` (declaration order is the sort order), then `bunx prisma migrate dev --name <name>`; (3) `bun run --filter server typecheck`, which fails if (1) and (2) differ. The classification prompt (built from `categoryLabels`), validation, filters and dropdowns follow on their own. To remove one, move its tickets to another category or `null` first, or the migration fails. The column stays a Postgres enum on purpose, so the database rejects unknown values; Prisma can't read the list from TypeScript.
- E2E specs keep literal role strings where they assert the API's JSON, since that tests the wire format rather than app code.

It is also declared **`required: true` with `defaultValue: "agent"`**, which mirrors the non-nullable column and types `user.role` as `"admin" | "agent"` instead of widening it with `| null | undefined` (`InferDBFieldOutput` adds those for `required: false`). The combination looks risky next to `input: false` but is not: in `better-auth/dist/db/schema.mjs`, `parseInputData` assigns `defaultValue` and `continue`s at line ~95, so the `"role is required"` throw at line ~103 is unreachable for any field that has a default. A required field **without** a default would throw on every create.

Role-based authorization is enforced **on the server** by `requireAdmin` (below). The client's `AdminRoute` only hides a page and does not protect data; never rely on it in place of the server check.

**Creating accounts.** There is deliberately no committed script for agent accounts — the admin UI in the current phase is meant to replace that path. To make one ad hoc, mirror `prisma/seed.ts`: `await auth.$context` → `ctx.internalAdapter.createUser({ email, name, emailVerified: true, role: "agent" }, { method: "email-password" })` → `ctx.internalAdapter.linkAccount({ userId, providerId: "credential", accountId: userId, password: await ctx.password.hash(pw) })`. Going through `internalAdapter` matters: it hashes with Better Auth's own configured hasher, so a row written directly to the table will not authenticate. Pass credentials via environment variables rather than writing them into a file. `agent@example.com` was created this way for local testing, and `e2e/seed-agent.ts` does the same in `helpdesk_test` on every E2E run.

**Server wiring** (`server/src/index.ts`):
- `app.all("/api/auth/*splat", toNodeHandler(auth))` is mounted **before `express.json()`**. Order matters — the JSON parser would consume the request body and break every auth endpoint. Keep any new middleware that reads the body below this line. (`*splat` is Express 5 wildcard syntax.)
- **Rate limiting runs only in production**: `rateLimit: { enabled: IS_PRODUCTION }` (`NODE_ENV === "production"`), which also gates the per-account throttle below. This matches Better Auth's own default (`enabled: options.rateLimit?.enabled ?? isProduction` in `dist/context/create-context.mjs`), stated explicitly so it doesn't hinge on that default. Dev and Playwright runs sign in unthrottled. **A deploy without `NODE_ENV=production` has no brute-force protection at all.** Better Auth reads the client IP only from headers and never from the socket, and without config it trusts a single-value `X-Forwarded-For`, which a caller can forge to get a new bucket on every request. So `index.ts` overwrites the `x-auth-client-ip` header (`CLIENT_IP_HEADER`) with Express's `req.ip` on every `/api/auth` request, and `auth.ts` reads only that header. **Behind a reverse proxy, set `app.set("trust proxy", <proxy address>)`**, or every client resolves to the proxy's IP and shares one sign-in bucket (3 requests per 10s), which locks everyone out. The limiter's store is in memory: it resets on restart and isn't shared across instances; switch to `storage: "database"` (this needs a `rateLimit` model) before running more than one.
- **Per-account sign-in throttle.** The built-in limiter keys only on IP + path (`customRules` can change `window`/`max` but not the key), so rotating addresses bypasses it. `hooks.before`/`hooks.after` in `auth.ts` count 401s on `/sign-in/email` per lower-cased email and return 429 after 5 failures in 15 minutes; a successful sign-in clears the count. It's in memory and production-only, like the IP limiter. The trade-off: anyone can lock a known email out for 15 minutes, which is the price of capping guesses.
- `requireAuth` (`server/src/middleware/requireAuth.ts`) resolves the session via `auth.api.getSession` with `fromNodeHeaders(req.headers)`, replies `401 {"error":"Unauthorized"}` when absent, and otherwise populates `req.user` / `req.session`. Those are declared in `server/src/types/express.d.ts`. Use it on every protected route; `/api/me` is the reference example.
- `requireAdmin` (`server/src/middleware/requireAdmin.ts`) replies `403 {"error":"Forbidden"}` unless `req.user.role === "admin"`. It reads `req.user`, so it must run **after** `requireAuth`. `index.ts` mounts both on the whole prefix — `app.use("/api/users", requireAuth, requireAdmin)` — so any route added under `/api/users` is admin-only without its own guard. Put other admin-only endpoints under a guarded prefix the same way. The role comes from the DB-backed session lookup on every request (no cookie cache), so a demotion takes effect on the next request.
- A JSON **error handler is mounted last** in `index.ts`. Keep it below every route: without it Express's finalhandler returns `err.stack` as HTML whenever `NODE_ENV` isn't `production`, and since `express.json()` runs before the `/api/users` guard, even an unauthenticated malformed body would get one. It shows `err.message` only when http-errors marks it `expose` (4xx from body parsing); otherwise it returns a generic `500` and logs the error on the server. Route handlers can just `throw`, because Express 5 forwards rejected promises here.
- CORS runs with `origin: process.env.CLIENT_URL, credentials: true`, and `CLIENT_URL` also feeds `trustedOrigins`. Auth is cookie-based, so a cross-origin caller must send credentials.

**Client wiring.** `client/src/lib/auth-client.ts` calls `createAuthClient()` with **no `baseURL`**, so requests go to the current origin's `/api/auth` — in dev that is the Vite proxy. Keep it that way rather than hardcoding a host. `authClient.useSession()` drives `ProtectedLayout` (redirects to `/login` while unauthenticated, renders `Navbar` + `Outlet` when signed in); `authClient.signIn.email` and `authClient.signOut` handle the transitions.

`role` reaches the client typed via the `inferAdditionalFields` plugin, in its generic form — `inferAdditionalFields<typeof auth>()` over a **type-only** import of the server's `auth`:

```ts
import type { auth } from '../../../server/src/lib/auth.ts'
```

This is the one place the client reaches across the workspace boundary, and it is deliberate: additional fields stay declared once, in `server/src/lib/auth.ts`, instead of being restated in a client-side schema that can drift from it. Add a field there and the client type follows with no second edit.

It works because the import is types-only. `verbatimModuleSyntax` erases it, so no server code reaches the bundle (grep the built JS for `prisma` — zero hits), and `tsc` tolerates the out-of-`include` files because `tsconfig.app.json` sets no `rootDir`, runs `noEmit`, and has `skipLibCheck` for the generated Prisma declarations. The cost is real but small: ~12 server and generated-Prisma files join the client program, and a cold `tsc -b` runs ~1.8s. Keep the import `import type`, never a value import.

**Client route gating.** `AdminRoute` (`client/src/components/AdminRoute.tsx`) is a layout route that renders `<Outlet />` for `role === Role.admin` and otherwise redirects to `/`. Nest it inside `ProtectedLayout` — it assumes a session already exists and does not re-check. `Navbar` takes an `isAdmin` prop from `ProtectedLayout` (which already holds the session) and hides admin links for agents, so the navbar stays presentational rather than reading the session itself. If its prop list grows much further, pass `session.user` whole instead of adding a third flag.

**Environment.** `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `CLIENT_URL`, `INBOUND_EMAIL_SECRET`, the optional `MAILER_URL` + `MAILER_SECRET` (the mailer that emails replies; without both, replies are only stored), and the optional `OPENAI_API_KEY` (exported from `env.ts` unvalidated; without it the AI endpoints answer 503, so dev and E2E runs start without one). The four after `DATABASE_URL` are validated in `server/src/lib/env.ts`, which throws at import when any is missing or empty — the server (and the seed, which imports `auth`) refuses to start rather than letting Better Auth fall back to its public default secret outside production or `cors` fall back to `*`. Import them from there instead of reading `process.env` directly. The seed additionally needs `ADMIN_EMAIL`, `ADMIN_PASSWORD`, and optionally `ADMIN_NAME` (defaults to "Admin"). `NODE_ENV` is not validated but matters: only `production` turns on sign-in rate limiting (above), and `start:test` runs with `test` from `server/.env.test`.

**Seeding** (`server/prisma/seed.ts`) is idempotent and safe against production. It validates the email shape and the password against Better Auth's own `minPasswordLength`/`maxPasswordLength`, refuses the placeholder `admin@example.com` when `NODE_ENV=production`, creates the user plus a `credential` account with a hashed password (mirroring what the disabled sign-up endpoint would do), and on re-run only ensures the `admin` role — **an existing password is never overwritten**. It also repairs a user left without a credential account by a half-failed run.

**Demo tickets:** `bun run --filter server db:seed:tickets` (`server/prisma/seed-tickets.ts`) adds 100 realistic tickets to a dev database, spread over statuses, categories (some unclassified), senders, active agents and the last 120 days, for trying out sorting and filtering. It is deterministic and idempotent (fixed `messageId`s `<seed-ticket-N@helpdesk.local>`, `skipDuplicates`), writes through Prisma directly because the webhook only creates open, unclassified tickets, and refuses to run with `NODE_ENV=production`. `bun run --filter server db:seed:replies` (`server/prisma/seed-replies.ts`) then adds a 20-message conversation to ticket 12 (agent and customer alternating, each at least 10 lines, written for that ticket's "App crashes when uploading a photo"), for a long thread to read and summarize; it does nothing if the ticket already has replies.

## Inbound email

`POST /api/webhooks/inbound-email` (`server/src/routes/webhook.ts`) turns an email into a `Ticket`. It is fed by our own `mailer` (see *Mail server* below) and takes a provider-neutral JSON body (`inboundEmailSchema` in `core/src/schemas/tickets.ts`, where the other ticket schemas belong too): `senderEmail`, `senderName` and `body` are required; `subject` (blank becomes `"(no subject)"`), `bodyHTML`, `messageId`, `inReplyTo` and `references` (an array of Message-IDs, max 100, each capped at 998 like `messageId`) are optional. A SendGrid/Mailgun adapter should map its own format onto this rather than replace it.

- **Auth is a shared secret, not a session:** `requireWebhookSecret` (`server/src/middleware/requireWebhookSecret.ts`) compares the `X-Inbound-Secret` header to `INBOUND_EMAIL_SECRET` with `timingSafeEqual` and replies `401 {"error":"Unauthorized"}` otherwise. It is mounted on the whole prefix (`app.use("/api/webhooks", requireWebhookSecret, webhookRouter)`), so add future webhooks to `webhookRouter`. Never put `requireAuth` on it.
- **Dedupe by `messageId`:** providers redeliver on timeouts, so a `messageId` already stored on a ticket or a reply returns that ticket (`{ ticket }`) or reply (`{ ticket, reply }`) with `200` instead of `201`; a concurrent duplicate that hits a unique constraint (P2002) is answered the same way.
- **Threading:** when `inReplyTo` or any of `references` matches a ticket's `messageId` or one of its replies' `messageId`, the email becomes a `ReplySender.customer` reply on that ticket (`201 { ticket, reply }`, no new ticket), and a `resolved`/`closed` ticket goes back to `open` in the same transaction. An unknown thread falls through to a new ticket. The sender isn't checked against the ticket's, since anyone on CC may answer. Outbound agent replies have no Message-ID yet, so a customer answering an agent's email threads only through the earlier Message-IDs in `references`; record outbound Message-IDs when the provider is added.
- **Auto-resolve:** with `OPENAI_API_KEY`, a new ticket starts as `TicketStatus.new` (without it, `open`), and the webhook also queues it on `auto-resolve-ticket`. **The AI agent:** such a ticket is also assigned to the system user `AI` (`AI_AGENT_ID = "ai-agent"` in `server/src/lib/aiAgent.ts`, inserted by the `add_ai_agent` migration so every database has it). It has no account row, so it can't sign in, and it's excluded from `GET /api/users`, `findActiveUser` (PATCH/DELETE answer 404) and `activeAgentWhere` (not in `/assignees`, and PATCH rejects it with 400); when combining those filters with an `id`, use `AND: [...]`, since spreading `id` after them overwrites `id: { not: AI_AGENT_ID }`. The AI's replies have it as `authorId`, and the detail page shows it as "Assigned to: AI" (the picker shows a current assignee that isn't selectable). It stays assigned to a ticket it resolved; `openForAgent` (when the AI can't answer, on the last retry, or when queueing fails) sets `open` and unassigns it, and a customer email threaded onto a ticket it holds unassigns it too, so a person takes over. The worker, `autoResolveNewTicket` (`server/src/lib/autoResolveTicket.ts`), moves it to `processing`, sends it with `server/knowledge-base/knowledge-base.md` (read on every job, so edits apply without a restart; the knowledge base itself isn't escaped) to `autoResolveTicket` in `ai.ts` (`Output.object` `{ resolved, reply }`; the prompt escalates on the knowledge base's escalation rules, partial answers, requests needing a person, or low confidence), then either stores the answer as a `ReplySender.ai` reply and sets `resolved` in one transaction, or sets `open` for an agent. Every step updates only while the status is still `new`/`processing`, so an agent's change in the meantime wins. On the last retry, or when the job can't be queued, `openForAgent` opens the ticket so it's never left hidden. `new` and `processing` are hidden from `GET /api/tickets` (`VISIBLE_TICKET_STATUSES` in `core/constants/ticketStatus`). A customer email threaded onto an AI-resolved ticket reopens it like any other. With the mailer configured the AI's answer is emailed like an agent reply (see *Emailing replies*).
- New tickets are `TicketStatus.new` and assigned to the AI agent (with AI) or `open` and unassigned, with `category: null`. **Classification runs as a pg-boss job:** for a new ticket (not for threaded replies or dedupe hits), the webhook queues `{ id, subject, body, senderName }` on `classify-ticket` (`boss.send`, a single insert, before the `201`), so the provider never waits on the model; a failed send is logged and the ticket stays unclassified rather than the webhook answering 500. pg-boss (`server/src/lib/queue.ts`) stores jobs in its own `pgboss` schema in the same database, which it creates and migrates itself (Prisma's migrations don't manage it), so a job survives a restart. The worker, `classifyNewTicket` (`server/src/lib/classifyTicket.ts`), sends the subject, sender and body to `classifyTicket` in `server/src/lib/ai.ts` (`gpt-6-luna`, `Output.choice` over `TicketCategory`, same `<ticket>` framing as the other prompts; the category list in the system prompt is built from `categoryLabels` in `core/constants/ticketCategory`, values and labels only, so a new category needs no prompt edit; the model may also answer `unclear` for gibberish or a ticket it can't place, which `classifyTicket` returns as `null` and leaves the ticket unclassified) and writes the category with `updateMany({ where: { id, category: null } })`, so a category an agent set in the meantime (or a retry) never overwrites it. A thrown error fails the job, and pg-boss retries it 3 times with exponential backoff from 30 s. `createQueue` only creates a missing queue, so change the retry options of an existing one with `boss.updateQueue`. Without `OPENAI_API_KEY` or the mailer, `index.ts` never starts pg-boss (`startQueue` registers the AI workers only with the key, the email worker only with the mailer) and the webhook queues nothing (E2E runs this way); with it, `boss.stop()` on SIGINT/SIGTERM lets a running job finish. `assignedToId` holds a `User.id` but is deliberately a plain column with no Prisma relation. Use the generated `TicketStatus` / `TicketCategory` enums on the server and `core/constants/ticketStatus` / `ticketCategory` elsewhere, never string literals, as with `Role`.
- `/api/webhooks` has its own `express.json({ limit: "35mb" })` (25 MiB of attachments as base64, plus the bodies), in the same mount as the secret and **after** `requireWebhookSecret` (so an unauthenticated caller can't make the server read that much), and mounted before the global 100 kB parser, which then skips those requests; larger requests get a 413. The schema caps `body` at 50 000 and `bodyHTML` at 100 000 characters (400), and the header fields at their RFC limits (`senderEmail` 254, the rest 998). `body` may be blank when the email has attachments or `bodyHTML` (a file on its own, a pasted screenshot), and is then stored as `(no text)`.
- **Attachments:** `attachments` on the webhook body (`{ filename, contentType, size, contentId?, content? }`, `content` base64) become `Attachment` rows, in Postgres (`data Bytes?`), created with the ticket or reply in one write. `replyId` is null for the ticket's own email. Limits are in `core/constants/attachment`: 10 MB per file, 25 MB per email, 20 stored files, and over them the webhook answers 400. A file sent **without `content`** is one over the limits: it's stored with `tooLarge: true`, listed by name, and only the original email has it, so an oversized file never loses the ticket. Sender-controlled text is cleaned rather than rejected: control characters leave `filename` (Postgres text can't hold NUL, and that 500 would make the mailer retry forever), a bad `contentType` becomes `application/octet-stream`, a bad `contentId` is dropped. **Never select `Attachment.data` outside the download route:** use `attachmentSelect` (`server/src/lib/attachments.ts`), which `tooLarge` exists for, since Prisma can't test `data` for null without reading it. `GET /api/tickets/:id` lists the ticket's own files and `GET /api/tickets/:id/replies` each reply's. `GET /api/tickets/:id/attachments/:attachmentId` downloads one, always as `Content-Disposition: attachment`, with the stored type only for `INLINE_IMAGE_TYPES` (png, jpeg, gif, webp; never SVG) and `application/octet-stream` otherwise, plus `nosniff` and `CSP: sandbox`, so sender-made HTML never runs on our origin. `res.attachment` sets a type from the extension, so the type has to be set after it. An `<img>` ignores `Content-Disposition`, so inline images still render: `emailContent` (`client/src/lib/emailHtml.ts`) sanitizes the HTML, rewrites matching `cid:` links to that URL, and returns the files left for `AttachmentList`. Render email HTML through `emailContent` only. The AI never sees file contents: names go in the prompt (`TicketContext.attachments`, inside `<ticket>`, escaped), and auto-resolve escalates when the answer may depend on them. There's no virus scanning; add it before production.

## Mail server (`mailer`)

`mailer/` is a separate workspace and process (Bun + Express, port 3002) for our own mail server, instead of SendGrid/Mailgun. It is not part of `bun run dev`, since it won't start without `mailer/.env` (`mailer/.env.example`; `src/env.ts` throws at import on a missing setting).

- **Inbound** (`src/inbound.ts`): every `POLL_INTERVAL_MS` (default 30 s, the next pass scheduled when the last one ends, so passes never overlap) it connects with `imapflow`, parses each email in `IMAP_MAILBOX` with `mailparser` (`keepCidLinks: true`, or inlined images as `data:` URLs would push `bodyHTML` past the webhook's cap) and maps it with `toInboundEmail` onto `InboundEmailInput`, so a change to the webhook's schema fails the mailer's `tsc`. It posts it to `WEBHOOK_URL` with `X-Inbound-Secret`, one email at a time. Attachments go along as base64, in order until a limit in `core/constants/attachment` is reached; one that doesn't fit is sent without `content`, so the webhook lists it as too large. **2xx** (stored or duplicate) moves it to `IMAP_PROCESSED_MAILBOX`; **400/413** (invalid or too large, which a retry would never fix) to `IMAP_FAILED_MAILBOX`; anything else, a 401 from a wrong secret included, leaves it in the inbox for the next pass. Both folders are created when missing. A move that fails after a successful POST only means a redelivery, which the webhook's `messageId` dedupe absorbs. Missing fields (no From, empty body) are sent blank on purpose, so the webhook's validation decides.
- **Outbound** (`src/outbound.ts`): `POST /send` behind `X-Mailer-Secret` (`MAILER_SECRET`, `timingSafeEqual`), body `sendEmailSchema` (`core/schemas/email`: `to`, `subject`, `text`, optional `html`, `inReplyTo`, `references`), sent through nodemailer's SMTP transport from `MAIL_FROM`. Returns `200 { messageId }`, the Message-ID to store on the agent's `Reply.messageId` so the customer's answer threads; `400` for an invalid body, `502` when SMTP fails. The SMTP connection is checked (`transporter.verify()`) and logged at startup. The server calls it from `sendReplyEmail` for agent and AI replies (see *Emailing replies*).

## Architecture

- **Monorepo**: root `package.json` defines `workspaces: ["client", "server", "mailer", "core"]`; each workspace has its own `package.json` and `tsconfig.json`. Use `bun run --filter <client|server> <script>` (or the root `dev`/`dev:server`/`dev:client` scripts) rather than `cd`-ing in for routine runs.
- **Shared code (`core`)**: anything both client and server need at runtime lives in `core`, never duplicated per side. Zod schemas for API payloads go in `core/src/schemas/` (e.g. `createUserSchema` / `updateUserSchema` in `schemas/users.ts`, `inboundEmailSchema` in `schemas/tickets.ts`, `createReplySchema` in `schemas/replies.ts`, used by `UserForm` for the form and by `POST` / `PATCH /api/users` for the request body), so the form and the server enforce the same rules. The package ships TypeScript source with no build step (Vite and Bun read it directly), is depended on as `"core": "workspace:*"`, and exposes each module through its `exports` map — import `core/schemas/users` or `core/constants/role`, and add an `exports` entry for every new module. Keep it free of server-only code (Prisma, Better Auth), since it ends up in the client bundle. Values that can't be read from the client, like Better Auth's password bounds, are restated as constants there and must be kept in sync by hand.
- **Server**: Express 5 + TypeScript, run directly via Bun (no build step for dev). API routes live under `/api/*`. PostgreSQL via Prisma 7 (`@prisma/adapter-pg`); the client is generated to `server/generated/prisma` and imported through the singleton in `server/src/lib/db.ts` — import `prisma` from there rather than constructing a new `PrismaClient`. **After a migration, run `bun run --filter server db:generate`** (and restart a running server): after `prisma migrate dev` added `Ticket.resolvedAt`, the runtime client still rejected the field (`PrismaClientValidationError`, every PATCH a 500) until it was regenerated, though `tsc` passed. Validate request bodies with `validate(schema, req, res)` from `server/src/lib/validate.ts` (`const body = validate(...); if (!body) return;`), and query strings with `validateQuery` from the same file: each returns the parsed data, or replies `400 {"error": <first issue message>}` and returns `undefined`. Use it instead of an inline `safeParse`, so every route answers invalid input the same way; `users.ts` and `webhook.ts` are the reference.
- **Client**: Vite + React 19 + TypeScript, with Tailwind v4 and shadcn/Base UI for styling (see *UI components* above). Routing is `react-router` (routes in `client/src/App.tsx`); `ProtectedLayout` gates routes on a Better Auth session and redirects to `/login`, and `AdminRoute` nests inside it to gate `/users` on the admin role. In dev, Vite proxies `/api` to `http://localhost:3001` (see `client/vite.config.ts`), so the client always calls relative `/api/...` paths rather than a hardcoded host. Server data is loaded with TanStack Query (`useQuery`, provider in `client/src/main.tsx`) over axios; `retry` is off by default.
- **Linting**: client uses `oxlint` (`client/.oxlintrc.json`); no lint config exists for the server yet.

### Target architecture (per `tech-stack.md` / `implementation-plan.md`, not yet implemented)

- Admin-facing user management: an admin creates and manages agent accounts. In progress — listing is done (`GET /api/users` returns `id, name, email, role, createdAt` via an explicit `select`; `UsersPage` renders it). A `databaseHooks.session.create.before` hook in `auth.ts` refuses sessions for deleted users with the same "Invalid email or password" as a wrong password. **Every query that lists or looks up users for use must filter `deletedAt: null`** (`findActiveUser` in the users route); only the email-uniqueness checks deliberately see deleted rows, so a deleted user's email stays reserved. `usersRouter` is mounted on the same line as the guard (`app.use("/api/users", requireAuth, requireAdmin, usersRouter)`), so add new user routes to that router.

- AI features via the Claude API: auto-classification, ticket summaries, and suggested replies, backed by a knowledge base.
